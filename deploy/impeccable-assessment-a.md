範圍：`frontend/src/views/Home.vue`，連同 `WebSources.vue`、`HistoryDatabase.vue`、`WorkflowExplorer.vue`。屬現有視覺語彙內的調整；保留炭灰、暖石、琥珀色、一鍵準備網址與檔案、目標輸入、歷史入口、三種語言、深淺色與設定。

## 判斷

這個首頁已有一致、沉穩的工作室風格。暖石背景、深色文字與琥珀細線，比通用白色工具介面更有個性。主要操作是清楚的兩步：加入資料，再描述問題。

最大的機會是讓「資料如何變成可探索的結果」直接看得懂。目前唯一插圖約 200px 寬，沒有承擔說明任務，手機版更完全隱藏；有用的流程說明卻和連線資訊一起收起。進一步簡化應減少重複提示與無效高度，把騰出的空間交給有意義的視覺說明。

## 優先改善

### 1. [P2] 窄屏先讓人看見任務全貌

**問題與影響：** 窄屏資料區前已有約 409px 的導覽、介紹和區塊標題；目標欄 y≈783，開始按鈕 y≈1193。使用者第一次看到表單時無法迅速掌握「填這兩項就能開始」。

**具體做法：** 把工作室介紹縮為一句，把 NEW EXPLORATION 縮成較小區標；資料區保留網址框與清楚的檔案按鈕，合併重複說明。手機讓步驟 1／2 更緊密，保留至少 44px 的主要控制高度。先改善內容高度，再評估是否需要貼底按鈕。

**依據：** `Home.vue:14`、`:27`、`:32`、`:54`、`:444`、`:464`；窄屏 DOM 位置與截圖。

**適用指令：** i-layout、i-distill、i-adapt。

### 2. [P2] 用有意義的圖取代部分說明，讓結果可預期

**問題與影響：** 現有文件與球體插畫有風格，但只像裝飾；手機 `display:none`。使用者讀完介紹仍主要靠文字猜測會得到甚麼。展開流程後又先看到連線技術資訊。

**具體做法：** 用 imagegen 製作同一炭灰／暖石／琥珀世界的「資料 → 人物關係 → 報告」視覺；文字標籤用介面原生文字保留三語，不讓圖片負責精確字樣。把三個成果線索放在表單旁或上方，手機改成很矮的橫向圖，不直接隱藏。完整五步解說仍可展開，連線狀態獨立保持收合。

**依據：** `Home.vue:20`、`:74`、`:85`、`:439`、`:474`；流程展開 AX 顯示 Graphiti + Neo4j 先於 From sources to insight。

**適用指令：** i-layout、i-clarify、imagegen。

### 3. [P2] 歷史紀錄先顯示使用者能辨認的內容

**問題與影響：** 四筆實際紀錄的截斷標題與描述幾乎相同，頂部是 SIM 編號和 ◇◈◆，文件框又占很大面積。使用者要逐張開啟才能分辨內容與可用結果。

**具體做法：** 首行保留較完整目標摘要與日期，第二行用簡短文字說明「報告可查看」等狀態；檔案名稱降為輔助列，SIM 編號留在詳細資料。較長歷史可用緊湊列表；所有既有回放按鈕留在詳情內。不要新增未經確認的生成標題或資料欄位。

**依據：** `HistoryDatabase.vue:42`、`:63`、`:89`、`:96`；四張相似歷史卡的桌面與手機截圖。

**適用指令：** i-layout、i-clarify、i-distill。

### 4. [P2] 每一欄只保留一個最有用的提示

**問題與影響：** 目標區同時有 Your own words are enough、長 placeholder、欄位下說明、Need a starting point，以及底部再提醒資料加目標；來源區也有可只用檔案、開始時擷取、限制摘要、上傳說明。資訊不是錯，但重複閱讀減慢操作。

**具體做法：** 每欄採「短標籤＋具體範例＋需要時才出現的狀態」。目標欄保留一個實際問題範例；底部提示隨缺少項目精準變化，不再泛泛重述整個流程。用深色文字清楚保留重要標籤，用琥珀只標操作與當前步驟。

**依據：** `Home.vue:53`、`:55`、`:56`、`:64`、`:150`；`WebSources.vue:3`、`:7`、`:28`。

**適用指令：** i-distill、i-clarify。

### 5. [P1，來源確認的保存邊界] 「所有歷史」不能無聲地只剩二十筆

**問題與影響：** 目前來源固定呼叫 `getSimulationHistory(20)`，畫面沒有「更多」或分頁。現有只有四筆，未實測第二十一筆；但若服務遵守這個上限，較早紀錄將沒有可見入口。這是使用者要求保留全部歷史時要先確認的邊界。

**具體做法：** 對照服務回傳能力，保留完整歷史可達性；若採分頁或「載入更多」，至少呈現剩餘內容入口，不能為簡化而只留幾張最近卡片。

**依據：** `HistoryDatabase.vue:28`、`:430`；`frontend/src/api/simulation.js:186` 把 limit 傳給 `/api/simulation/history`。這是來源風險，並非宣稱實際已丟失紀錄。

**適用指令：** i-harden、i-layout。

## 版面七項診斷

| 面向 | 判斷與證據 |
|---|---|
| 閱讀順序 | 桌面是標題 → 建立探索 → 兩個輸入 → 開始，順序成立。手機導覽變兩排，前導區與區標仍占高度，核心第二步較深。 |
| 分組 | 兩個輸入同一主容器合理；來源內網址／檔案的距離合理。連線與流程被同一摺疊容器綁住，意義不同。 |
| 節奏 | 30px 雙欄間隔與主要區的 20–28px 留白足夠；來源側多條短提示使垂直節奏零碎，歷史內的文件框、分隔線與卡框層層包覆。 |
| 結構 | 桌面雙欄、手機單欄匹配兩步填寫。歷史四張大卡不適合每筆都高度相似的實際資料；更緊湊清單值得採用。 |
| 密度 | 桌面操作區密度適中；手機密度偏低而需長捲動。技術狀態收合可保留，簡化應減文字與容器，而非刪功能。 |
| 適應 | 1423px、854px、434px 未觀察到橫向溢出；≤760px 變單欄，≤580px 插圖／GitHub 隱藏。三語元件存在，但未切換語言；200% zoom 未測。窄屏錯誤雙按鈕由 column-reverse 改視覺順序，來源顯示它可能與 DOM 焦點順序相反，需在後續真實錯誤情境驗證。 |
| 極端情境 | 實際長中文需求在回放彈窗可換行閱讀；主列表強制截短使不同紀錄相似。空歷史有插圖與文案，錯誤有重試，為來源確認；大量歷史的二十筆上限需處理。收合摘要實測高約36px，觸控目標可增至44px。 |

## 情緒與不同使用者

開頭的暖色、日常問題範例與兩步編號降低戒心，是正向起點。低點出現在等待理解「分析以後是甚麼」以及在歷史中尋找特定一次探索；兩處都可以用結果預覽與更可辨認的紀錄改善。實際完成分析的峰值與最後一步未測，不能評斷整個產品的完成體驗。

- **初學者 Jordan：** 第一個輸入清楚，但關係、模擬與報告多靠一句總介紹理解；Graphiti + Neo4j 與 Env Setup 不符合沒有背景的使用者。
- **手機使用者 Casey：** 目標欄與開始按鈕離首屏較遠，插圖消失；歷史每筆仍是大卡，四筆已形成長列表。
- **依賴鍵盤或輔助工具的 Sam：** 彈窗 Escape、回到開啟位置實測通過；來源與目標都有 label。歷史卡只把截短目標當可讀名稱，相似紀錄不容易區分；錯誤狀態雙按鈕順序需要實測。

## 值得保留與小項目

1. 溫暖高對比的方向、兩步編號與單一主操作已形成穩定基礎。
2. 網址／檔案與目標同頁，保留了使用者的上下文，無需新增精靈式多頁步驟。
3. 歷史彈窗與流程 tab 已有鍵盤與焦點設計；簡化時要保留。

小項目：歷史區標題目前是 span 而非真正標題；原始碼存在多輪覆寫樣式，修改時應以最末生效規則為準。現有英文回放 Step3／Step5 不支援歷史回放的提示容易被理解成資料遺失，可改成正面、清楚地說明可查看的保存內容，勿承諾尚未存在的回放能力。
